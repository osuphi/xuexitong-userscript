# 暂停误判修复（F17）

修复「调节音量后，把鼠标移出浏览器，视频被暂停且再也不自动恢复」。返回 [README](../README.md)。

## 现象

1. 在播放器里调一下音量（或点静音）；
2. 把鼠标移出浏览器窗口；
3. 视频被暂停，之后**再也不会自动恢复**，只能手动点播放。

## 根因

脚本里有一条用于"尊重用户"的判定：**如果暂停发生在用户刚操作过播放器之后，就认定是用户主动暂停，脚本从此不再抢播**（这是上游 #26/#32/#55 的设计，用来避免无差别 `play()` 触发风控）。

问题在于：**"调音量"也被算成了"刚操作过播放器"**。

`_bindUserInteractionWatch()` 在播放器文档上监听 `pointerdown` / `click` / `keydown`，任何一次操作都会刷新 `_lastUserInteractionTs`。于是：

- 调音量 → `_lastUserInteractionTs = T`
- 鼠标移出 → 平台防挂机代码调用 `video.pause()`（约 T+1.3 秒）
- `pauseGuard` 看到"1.5 秒内有过用户操作"，**把这个暂停当成用户意图放行**；
- `_handleVideoPause()` 看到"2.5 秒内有过用户操作"，把 `_userPaused` 置为 `true`；
- 此后 `_tryResumePlayback()` 一律提前返回 → **永不恢复**。

用户提供的诊断报告可直接复现这条时间线：

```
19:03:23.506  记录用户的静音选择：非静音      ← 调音量（volumechange）
19:03:24.648  记录用户的静音选择：非静音      ← 继续调
19:03:25.942  检测到用户主动暂停：脚本不再自动恢复播放
19:03:27.378  起 每秒一行"检测到视频暂停且进度停滞，按有界策略尝试恢复播放..."
19:04:27.377  （同样的日志持续了整整 1 分钟）
```

## 修复内容

1. **音量/静音操作不再计入"暂停意图"**：新增 `_isVolumeControlEvent(ev)`，判断事件目标是否属于音量滑杆（`input[type=range]`）、`vjs` 音量条、静音按钮，或 id/class 含 `volume` / `mute` / 音量 / 静音的元素（向上最多找 4 层）。命中时只更新 `_lastVolumeInteractionTs`，**不更新** `_lastUserInteractionTs`。
   - 效果一：鼠标移出时平台的 `pause()` 会被 `pauseGuard` 正常拦截 —— 视频根本不会暂停；
   - 效果二：即使因其他路径被暂停，也不会被误判成用户操作，会自动恢复。
   - 该判定只读事件目标，**不拦截事件、不调用 `preventDefault`**。
2. **删掉每秒一次的误导性日志**：原来暂停后无论是否会真的恢复，都会每秒打印一行"按有界策略尝试恢复播放..."；实际上 `_tryResumePlayback` 因 `_userPaused` 直接返回，等于一边刷屏一边什么都没做（实测 60 行/分钟）。现在是否发起恢复由 `_tryResumePlayback` 自己决定并打印。
3. **"用户暂停"提示改为节流输出**：新增 `_noteUserPausedStall()`，处于该状态时**每分钟最多提示一次**；面板状态行也新增 `用户暂停: 是（不自动恢复）/ 否`，一眼能看出脚本为什么不动作。
4. **诊断报告新增启动探测**：`启动时探测 : 沙箱 jQuery=… / 页面 jQuery=…（v…）/ 页面 $=…`，用来判断页面插件报错（例如 `getNiceScroll is not a function`）是否与本脚本补注入 jQuery 有关。

## 补充修复（F19）：点击恢复播放后立刻被暂停

**另一个同源问题**：视频处于暂停状态时，手动点击视频恢复播放，然后迅速把鼠标移出浏览器 —— 视频又停了，而且脚本判定为"用户主动暂停"、不再恢复。用户日志里一轮内重复出现了 4 次：

```
19:23:43.775  ===== '联觉对应关系的手法' 开始播放 =====   ← 点击恢复播放
19:23:44.111  检测到用户主动暂停                          ← 0.34 秒后鼠标移出被暂停
```

**原因**：原判定只看"用户刚操作过播放器"，而"点击恢复播放"同样是一次操作。用户刚按过播放，脚本却把紧随其后的暂停记成他的意图 —— 语义上自相矛盾。

**修复**：给判定补上"用户意图的方向"这一维。

- `_handleVideoPlay()`：如果这次 play 紧跟在某次用户交互之后（间隔 ≤ `userIntentMatchMs`，默认 800ms），记下 `_lastUserPlayTs`；
- `_wasJustUserResumed(now)`：判断"用户刚亲手把视频点开播"（那次 play 由最近一次交互触发，且仍在 `userResumeGraceMs` 宽限期内，默认 3000ms）；
- `_isUserPauseIntent(now)`：只有"用户在 `userPauseWindowMs` 内操作过"**且**"不是刚点开播"时，才认定为用户主动暂停；
- `pauseGuard` 同步使用 `_wasJustUserResumed()`：这种暂停直接拦截，视频根本不会停。

判定矩阵（已在测试里固化）：

| 场景 | 判定 |
| --- | --- |
| 点恢复播放后 0.4 秒被暂停 | 不算用户意图（拦截 + 不置 `_userPaused`） |
| 视频已播 30 秒，用户点暂停 | 算用户意图（尊重用户） |
| 恢复播放后 1 秒又点一次暂停 | 算用户意图（新交互晚于那次 play） |
| 交互后超过窗口 | 不算用户意图 |
| 从未交互 | 不算用户意图 |
| 只有交互、没有 play 记录 | 算用户意图 |

诊断报告新增 `lastUserInteractionMsAgo` / `lastUserPlayMsAgo` / `userPauseIntentNow` 三个字段，这类"误判"以后看报告就能直接定位。
